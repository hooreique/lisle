# Lisle Input Method Specification

## 1. 문서의 지위

이 문서는 Lisle의 사용자 관찰 가능 동작을 정의하는 규범 문서이다. 입력기
프레임워크, 프로그래밍 언어, 프로세스 구조, 저장 형식과 같은 구현 선택은 이
문서의 범위가 아니다. 구현 세부사항이 이 문서와 충돌하면 이 문서가 우선한다.

이 문서에서 다음 표현은 규범적 의미를 갖는다.

- **반드시**: 준수하는 구현이 지켜야 하는 요구사항이다.
- **해서는 안 된다**: 준수하는 구현이 금지해야 하는 동작이다.
- **할 수 있다**: 사용자 관찰 가능 결과가 같을 때 허용되는 구현 선택이다.

명시되지 않은 동작을 정해야 할 때는 다음 우선순위를 따른다.

1. 사용자가 이미 확정한 텍스트를 손실하거나 중복하지 않는다.
2. 호스트 프로그램의 일반적인 단축키와 편집 동작을 보존한다.
3. 활성 조합을 암묵적으로 취소하기보다 확정한다.
4. 입력 상태와 조합 상태를 포커스가 있는 편집 문맥 밖으로 옮기지 않는다.
5. 같은 물리 입력과 상태에는 같은 결과를 낸다.

## 2. 제품 범위

Lisle은 GNOME Wayland 환경에서 사용하는 한글 입력기이다. 하나의 표시 입력
소스 안에서 다음 두 입력 상태를 제공한다.

- **한글 상태**: Cole Sebeol 글쇠 배열과 조합 규칙으로 한글을 입력한다.
- **로마자 상태**: Colemak 글쇠 배열로 로마자를 입력한다.

Lisle은 다음을 책임진다.

- 물리 글쇠를 대표 글쇠로 식별한다.
- 왼쪽과 오른쪽 Shift를 구분하여 입력 상태를 선택한다.
- 한글 조합의 preedit, 확정, 취소와 편집 경계를 관리한다.
- 로마자 출력과 한글 상태의 단축키를 Colemak 기준으로 해석한다.
- 처리하지 않는 키와 단축키를 호스트 프로그램에 정확히 한 번 전달한다.
- 포커스, 활성화, 비활성화와 입력 소스 전환에서 조합 생명주기를 지킨다.

다음은 이 문서의 범위가 아니다.

- 후보 목록, 한자 변환, 자동 완성, 맞춤법 교정
- 사용자 사전과 학습
- 키 반복 속도와 운영체제 전역 키보드 설정
- 화면 표시기, 설정 화면과 배포 방식
- 입력기와 데스크톱 환경 사이의 구체적인 통신 방식

## 3. 용어

### 3.1 글쇠

- **대표 글쇠**: 물리적인 글쇠 위치를 표준 미국식 Qwerty 키보드에 인쇄된
  이름으로 부르는 기준 이름이다. 운영체제의 현재 XKB 배열이나 호스트가
  보고한 문자와 독립적이다. 예를 들어 물리적 Qwerty `K` 위치는 언제나 대표
  글쇠 `k`이다.
- **대표 글쇠 표기**: `k f x`, `j k f`, `v f`처럼 대표 글쇠를 입력 순서대로
  나열한 표기이다. 소문자는 Shift 없이 누른 글쇠, 대문자 또는 shifted symbol은
  Shift와 함께 누른 글쇠를 뜻한다.
- **아랫글쇠**: Shift 없이 누른 대표 글쇠의 출력이다.
- **윗글쇠**: Shift와 함께 누른 대표 글쇠의 출력이다.
- **source key**: 자모가 어느 대표 글쇠에서 왔는지 나타내는 입력 출처이다.
  같은 Unicode 자모를 내는 글쇠 사이의 조합 정책이 다를 수 있으므로 조합이
  끝날 때까지 보존해야 한다.

### 3.2 underlying roman layout

- `underlying roman layout`은 번역하지 않고 이 이름으로 쓴다.
- Lisle의 `underlying roman layout`은 Colemak이다.
- 로마자 상태의 printable 출력과 한글 상태의 로마자 단축키 해석에 사용한다.
- 한글 자모 배정과 한글 상태의 문장부호 출력에는 사용하지 않는다.
- 대표 글쇠와 underlying 글쇠는 다를 수 있다. 대표 글쇠 `j k f`는 Colemak
  underlying 글쇠로 `n e t`이다.

### 3.3 조합과 호스트

- **편집 문맥**: 한 호스트 프로그램 안에서 preedit와 확정 텍스트가 적용되는
  포커스 대상이다. 서로 다른 창, 탭, 입력 필드 또는 입력 세션은 입력기
  프레임워크가 구분할 수 있는 범위에서 서로 다른 문맥이다.
- **활성 조합**: 아직 호스트 문서에 확정되지 않은 현재 자모 입력 스택이다.
- **preedit**: 활성 조합을 사용자에게 보여 주는 임시 텍스트이다. 확정 텍스트와
  동시에 문서에 중복되어서는 안 된다.
- **Commit**: 텍스트를 호스트 문서에 정확히 한 번 확정하고 해당 활성 조합을
  비우는 동작이다.
- **Flush**: 활성 조합의 현재 visible text를 Commit하는 동작이다. 활성 조합이
  없으면 아무 텍스트도 만들지 않는다.
- **Clear**: Commit 없이 활성 조합을 비우는 동작이다. 명시적 취소 또는 복구
  상황에서만 사용한다.
- **Forward**: Lisle이 소비하지 않은 키 또는 호스트 동작을 호스트에 정확히 한
  번 넘기는 동작이다.
- **FlushThenEmit**: Flush한 다음 printable text를 Commit하는 동작이다.
- **FlushThenForward**: Flush한 다음 키 또는 호스트 동작을 Forward하는 동작이다.
- **partial composition boundary**: 활성 조합이 더 이어질 수 없어서 먼저 Flush
  또는 Clear해야 하는 입력 및 생명주기 경계이다.

## 4. 공통 불변조건

1. 한 편집 문맥의 활성 조합은 다른 편집 문맥에 표시되거나 확정되어서는 안 된다.
2. 한 물리 키 이벤트는 Lisle이 소비하거나 호스트에 전달해야 하며, 둘 다 해서는
   안 된다. 단, 경계 키를 전달하기 전에 조합을 Flush하는 것은 허용된다.
3. Commit된 텍스트는 같은 입력 처리 과정에서 preedit로도 남아서는 안 된다.
4. preedit 변경, Commit과 Forward의 순서가 관찰 가능하면 이 문서에 적힌 순서를
   지켜야 한다.
5. 활성 조합을 Flush한 뒤에는 빈 preedit가 되어야 한다.
6. 알 수 없는 키, 지원하지 않는 키와 입력기가 해석할 필요가 없는 키는 텍스트
   손실 없이 호스트로 전달해야 한다.
7. 키 press와 release를 모두 받더라도 printable text는 일반적으로 press에서만
   한 번 처리해야 한다. release가 같은 문자를 다시 만들어서는 안 된다.
8. 운영체제의 키 반복은 반복된 press 입력으로 처리하되 Shift 단일 탭으로
   오인해서는 안 된다.

## 5. 입력 상태

### 5.1 초기 상태와 문맥 범위

- Lisle이 새로 활성화되거나 명시적 선택 이력이 없는 새 편집 문맥이 시작되면
  로마자 상태여야 한다.
- 다른 호스트 프로그램, 창 또는 새 편집 문맥으로 포커스가 이동하면 이전 문맥의
  한글 상태를 새 문맥에 상속해서는 안 된다. 새 문맥은 로마자 상태에서 시작한다.
- 사용자가 다른 입력 소스로 전환했다가 Lisle로 돌아오면 로마자 상태에서
  시작한다.
- 입력 상태는 활성 편집 문맥의 일시적 상태이며 영구 전역 선호가 아니다.
- 이미 활성인 상태를 다시 선택하면 텍스트나 조합 상태를 바꾸지 않는다.

### 5.2 Shift 단일 탭

- 왼쪽 Shift 단일 탭은 로마자 상태를 절대 선택한다.
- 오른쪽 Shift 단일 탭은 한글 상태를 절대 선택한다.
- 이는 toggle이 아니다.
- Shift 단일 탭은 정확히 한쪽 Shift를 누른 뒤 유의미한 다른 입력 없이 같은
  Shift를 놓은 동작이다.
- Shift를 누른 동안 non-Shift 키가 발생하면 단일 탭 후보를 취소한다.
- 두 Shift가 같은 제스처에 참여하면 단일 탭 후보를 취소한다.
- 처음 누른 Shift 이외의 modifier가 눌리거나 상태가 바뀌면 후보를 취소한다.
- Caps Lock 상태는 유의미한 modifier로 보지 않으며 Shift 단일 탭 후보를
  취소하지 않는다.
- 키 반복이 발생한 Shift press는 단일 탭 후보를 취소한다.
- 취소된 후보는 해당 Shift를 놓을 때 상태를 바꾸지 않는다.
- Shift와 printable 글쇠의 조합은 현재 상태의 윗글쇠 입력이며 상태 선택이 아니다.
- Shift 단일 탭은 Shift 문자나 다른 텍스트를 출력하지 않으며 호스트에 별도
  키 입력으로 전달하지 않는다.
- 상태가 바뀔 때 활성 한글 조합이 있으면 먼저 Flush하고 새 상태를 적용한다.

### 5.3 Escape

- Escape는 취소가 아니라 Flush 및 로마자 상태 선택 경계이다.
- 활성 조합이 있으면 먼저 Flush한다.
- 로마자 상태를 선택한다.
- Escape 자체는 소비하지 않고 호스트에 Forward한다.
- 따라서 관찰 순서는 `Flush`, 상태 변경, `Forward(Escape)`이다.

## 6. 로마자 상태

### 6.1 printable 출력

로마자 상태의 표준 미국식 Qwerty 대표 글쇠는 다음 Colemak 출력으로 변환한다.
표에 없는 숫자와 문장부호는 대표 글쇠의 일반적인 US 출력과 같다.

```text
대표 글쇠: q w e r t y u i o p [ ] \
아랫글쇠: q w f p g j l u y ; [ ] \
윗글쇠:   Q W F P G J L U Y : { } |

대표 글쇠: a s d f g h j k l ; '
아랫글쇠: a r s t d h n e i o '
윗글쇠:   A R S T D H N E I O "

대표 글쇠: z x c v b n m , . /
아랫글쇠: z x c v b k m , . /
윗글쇠:   Z X C V B K M < > ?
```

- printable 입력은 변환된 Unicode scalar를 Commit한다.
- Caps Lock은 Lisle의 로마자 대소문자를 바꾸지 않는다. 대문자와 shifted
  symbol은 실제 Shift가 함께 눌린 경우에만 출력한다.
- Space와 호스트가 직접 제공한 printable whitespace는 그 의미를 보존한다.
- 물리 Tab과 Enter/Return은 printable 출력으로 변환하지 않고 호스트 동작
  키로 처리한다.
- dead key 또는 compose 기능처럼 Lisle이 정의하지 않은 문자 조합은 Lisle이
  임의로 재해석해서는 안 된다. 호스트가 처리할 수 있도록 전달한다.

### 6.2 로마자 상태 단축키

- Control, Alt, Super 또는 이와 동등한 비-Shift modifier가 포함된 키 조합은
  일반 printable 입력이 아니다.
- 단축키의 문자 의미는 Colemak `underlying roman layout`을 따른다.
- 예를 들어 대표 글쇠 `e`는 underlying `f`이므로 `Control+e`는 호스트에
  `Control+f` 의미로 전달한다.
- modifier 조합은 합성하지 않고 Colemak XKB가 해석한 원본 event를 호스트에
  통과시킨다. modifier 집합과 press/release identity는 그대로 보존한다.
- 시스템이 텍스트 입력기보다 앞에서 예약한 전역 단축키는 Lisle의 처리 대상이
  아니다.

## 7. Cole Sebeol 글쇠 배열

한글 상태의 자모 배정은 표준 미국식 Qwerty 대표 글쇠 위치에 놓인 공병우
세벌식 최종 배열을 바탕으로 하며, 아래 표가 Lisle의 최종 계약이다.

### 7.1 아랫글쇠

```text
대표 글쇠: ` 1 2 3 4 5 6 7 8 9 0 - =
출력:      ` ㅎ ㅆ ㅂ ㅛ ㅠ ㅑ ㅖ ㅢ ㅜ ㅋ - =
자모 자리: - 종 종 종 중 중 중 중 중 중 초 - -

대표 글쇠: q w e r t y u i o p [ ] \
출력:      ㅅ ㄹ ㅕ ㅐ ㅓ ㄹ ㄷ ㅁ ㅊ ㅍ [ ] \
자모 자리: 종 종 중 중 중 초 초 초 초 초 - - -

대표 글쇠: a s d f g h j k l ; '
출력:      ㅇ ㄴ ㅣ ㅏ ㅡ ㄴ ㅇ ㄱ ㅈ ㅂ ㅌ
자모 자리: 종 종 중 중 중 초 초 초 초 초 초

대표 글쇠: z x c v b n m , . /
출력:      ㅁ ㄱ ㅔ ㅗ ㅜ ㅅ ㅎ , . ㅗ
자모 자리: 종 종 중 중 중 초 초 - - 중
```

### 7.2 윗글쇠

```text
대표 글쇠: ~ ! @ # $ % ^ & * ( ) _ +
출력:      ~ ㄲ ㄺ ㅈ ㄿ ㄾ ^ & * ( ) _ +
자모 자리: - 종 종 종 종 종 - - - - - - -

대표 글쇠: Q W E R T Y U I O P { } |
출력:      ㅍ ㅌ ㄵ ㅀ ㄽ 5 6 7 8 9 { } |
자모 자리: 종 종 종 종 종 - - - - - - - -

대표 글쇠: A S D F G H J K L : "
출력:      ㄷ ㄶ ㄼ ㄻ ㅒ 0 1 2 3 4 "
자모 자리: 종 종 종 종 중 - - - - - -

대표 글쇠: Z X C V B N M < > ?
출력:      ㅊ ㅄ ㅋ ㄳ ? : ; < > !
자모 자리: 종 종 종 종 - - - - - -
```

표의 자모 이름은 사용자 표시를 위한 호환 자모이고 조합에서의 자리는 초성,
중성 또는 종성으로 고정된다. 같은 모양의 자모라도 자리 정보가 다르면 서로
대체할 수 없다.

### 7.3 sane-punctuation

- 위 표에서 자모가 아닌 printable 출력은 `sane-punctuation` 정책이다.
- 해당 입력은 `FlushThenEmit`으로 처리한다.
- 이 정책은 Colemak `underlying roman layout`과 독립적이다.
- 특히 윗글쇠 `N`, `M`, `?`는 각각 `:`, `;`, `!`을 출력하며, 윗글쇠
  `B`는 `?`, 윗글쇠 `:`은 `4`를 출력한다.
- 표의 ASCII 문장부호는 Unicode의 대응 ASCII scalar로 출력한다.

## 8. 한글 조합 모델

### 8.1 입력과 출력

한 입력을 처리한 결과는 논리적으로 다음 세 부분으로 구분되어야 한다.

- **committed text**: 이번 입력으로 새로 확정된 텍스트
- **preedit text**: 입력 처리 뒤 남은 활성 조합의 visible text
- **forwarded action**: Flush 뒤 호스트가 수행해야 하는 키 또는 편집 동작

이 구분은 외부 API 형태를 강제하지 않지만 결과와 순서는 보존해야 한다.

### 8.2 기본 음절 조합

- 내부 조합은 초성, 중성, 종성 자리를 구분한다.
- 유효한 현대 한글 초성 및 중성이 있으면 Unicode 완성형 한글 음절을 preedit로
  표시한다. 유효한 종성이 있으면 같은 음절에 포함한다.
- 완성 음절이 되지 못한 자모는 Hangul Compatibility Jamo로 표시하고
  확정한다. conjoining jamo scalar를 사용자 문서에 노출해서는 안 된다.
- 미완성 자모가 여러 개면 source key 입력 순서로 표시하고 확정한다.
- 활성 조합을 이루는 대표 글쇠 입력 스택을 보존해야 한다. Backspace와
  source-key-sensitive 조합은 이 스택을 기준으로 동작한다.

### 8.3 초성 선행 모아치기 정책

- Lisle은 full 모아치기를 지원하지 않는다.
- 초성이 먼저 결정된 뒤에만 중성과 종성을 어느 순서로든 받을 수 있다.
- `초성-중성-종성`과 `초성-종성-중성`은 같은 자모라면 같은 음절이 된다.
- 중성이나 종성이 초성보다 먼저 왔다면 나중 초성에 소급하여 붙여서는 안 된다.
- 초성만 있는 동안 두 번째 초성이 오면 8.5의 허용 조합을 먼저 시도한다.
  조합할 수 없으면 이전 초성을 Flush하고 새 초성을 시작한다.
- 중성 또는 종성이 온 순간 초성 조합 가능 상태는 닫힌다. 그 뒤 초성이 오면
  현재 조합을 Flush하고 새 초성을 시작한다.

규범 예시는 끝에서 명시적으로 Flush한 최종 텍스트이다.

```text
k f x -> 각
k x f -> 각
x k f -> ㄱ가
f k x -> ㅏㄱㄱ
```

### 8.4 중성 및 종성의 경계

- 이미 중성이 있는 조합에 새 중성이 오면 허용된 중성 조합을 먼저 시도한다.
- 조합할 수 없으면 기존 조합을 Flush하고 새 중성 단독 조합을 시작한다.
- 초성, 중성, 종성이 모두 있는 상태에서 새 중성이 오면 기존 음절을 Flush하고
  새 중성 단독 조합을 시작한다. 이전 종성을 새 음절의 초성으로 옮기지 않는다.
- 이미 종성이 있는 조합에 새 종성이 오면 허용된 종성 조합을 먼저 시도한다.
- 조합할 수 없으면 기존 조합을 Flush하고 새 종성 단독 조합을 시작한다.
- 초성이 없는 조합은 중성끼리 또는 종성끼리만 허용한다. 서로 다른 자모 자리가
  오면 기존 단독 조합을 Flush하고 새 단독 조합을 시작한다.
- 초성 없는 조합은 나중에 온 초성에 소급하여 붙지 않는다.

```text
k f r -> 가ㅐ
k f x z -> 각ㅁ
k x q f -> 갃
k x z -> ㄱㄱㅁ
f r -> ㅏㅐ
f x -> ㅏㄱ
x f -> ㄱㅏ
k f x f -> 각ㅏ
```

### 8.5 약한 아래 정책

다음 표에 명시한 서로 다른 자모 쌍만 순서와 무관하게 조합한다.

| 자리 | 첫째 | 둘째 | 결과 |
|---|---|---|---|
| 초성 | ㅇ | ㄱ | ㄲ |
| 초성 | ㄱ | ㅈ | ㅉ |
| 초성 | ㅈ | ㅂ | ㅃ |
| 초성 | ㄷ | ㅁ | ㄸ |
| 초성 | ㅅ | ㅎ | ㅆ |
| 중성 | ㅣ | ㅏ | ㅒ |
| 중성 | ㅣ | ㅡ | ㅢ |
| 중성 | ㅕ | ㅐ | ㅖ |
| 종성 | ㅇ | ㄴ | ㄶ |
| 종성 | ㅅ | ㄹ | ㅄ |
| 종성 | ㅂ | ㅆ | ㅈ |
| 종성 | ㅎ | ㅆ | ㄲ |

- 표의 각 쌍은 역순도 같은 결과를 낸다.
- 초성 같은 자모 반복은 된소리를 만들지 않는다. 초성 `ㄱ+ㄱ`, `ㅈ+ㅈ`,
  `ㅂ+ㅂ`, `ㄷ+ㄷ`, `ㅅ+ㅅ`은 각각 두 자모 위치로 남는다.
- 종성 `ㄱ+ㄱ -> ㄲ`, `ㅅ+ㅅ -> ㅆ`은 허용한다.
- 초성 약한 아래는 초성 조합 가능 상태 안에서만 적용한다. 중성 또는 종성이
  이미 온 뒤의 초성과 소급 조합해서는 안 된다.

```text
j k f -> 까       k j f -> 까       j f k -> 아ㄱ
k k f -> ㄱ가     k l f -> 짜       l l f -> ㅈ자
l ; f -> 빠       u i f -> 따       n m f -> 싸
d f -> ㅒ         d g -> ㅢ         k e r -> 계
k f a s -> 갆     k f q w -> 값     k f 3 2 -> 갖
k f 1 2 -> 갂
```

### 8.6 기본 종성 조합

약한 아래 표 외에 다음 순서의 종성 조합을 허용한다. 역순은 8.5에서 별도로
허용한 경우가 아니면 허용하지 않는다.

| 입력 | 결과 | 입력 | 결과 |
|---|---|---|---|
| ㄱ+ㄱ | ㄲ | ㄱ+ㅅ | ㄳ |
| ㄴ+ㅈ | ㄵ | ㄴ+ㅎ | ㄶ |
| ㄹ+ㄱ | ㄺ | ㄹ+ㅁ | ㄻ |
| ㄹ+ㅂ | ㄼ | ㄹ+ㅌ | ㄾ |
| ㄹ+ㅍ | ㄿ | ㄹ+ㅎ | ㅀ |
| ㅂ+ㅅ | ㅄ | ㅅ+ㅅ | ㅆ |

모든 조합 규칙은 자모 자리 안에서만 적용한다. 같은 Unicode 모양이 나타난다는
이유로 다른 자리의 자모를 전역 치환해서는 안 된다.

### 8.7 slash-nine(/9) 정책

대표 글쇠 `/`의 `ㅗ`와 대표 글쇠 `9`의 `ㅜ`는 source-key-special 중성이다.
대표 글쇠 `v`의 `ㅗ`, `b`의 `ㅜ`와 Unicode 자모는 같지만 정책은 다르다.

```text
/ f, f / -> ㅘ       / r, r / -> ㅙ       / d, d / -> ㅚ
9 t, t 9 -> ㅝ       9 c, c 9 -> ㅞ       9 d, d 9 -> ㅟ

v f -> ㅘ            v r -> ㅙ            v d -> ㅚ
b t -> ㅝ            b c -> ㅞ            b d -> ㅟ

f v -> ㅏㅗ          r v -> ㅐㅗ          d v -> ㅣㅗ
t b -> ㅓㅜ          c b -> ㅔㅜ          d b -> ㅣㅜ
```

- `/`와 `9`는 대응 기본 중성의 앞과 뒤에서 모두 조합한다.
- `v`와 `b`는 대응 기본 중성보다 먼저 입력된 경우에만 조합한다.
- 위 목록은 해당 source key 조합의 완전한 계약이다. 같은 Unicode 자모라는
  이유로 목록에 없는 순서를 추가해서는 안 된다.
- 이 정책은 `망했어ㅜㅜ` 같은 입력에서 뒤의 대표 글쇠 `b`가 앞 음절의 `ㅓ`와
  결합하여 `망했워ㅜ`가 되는 것을 막아야 한다.

### 8.8 preedit 표시

- 매 입력 뒤 preedit는 활성 조합의 현재 visible text 전체여야 한다.
- 완성 가능한 음절은 완성형 한글로, 미완성 자모는 호환 자모로 표시한다.
- 새 입력이 이전 조합을 Flush하고 새 조합을 시작하면 이전 visible text는
  committed text가 되고 새 조합만 preedit로 남는다.

```text
k       -> commit "",   preedit "ㄱ"
k x     -> commit "",   preedit "ㄱㄱ"
k f     -> commit "",   preedit "가"
k x f   -> commit "",   preedit "각"
/ f     -> commit "",   preedit "ㅘ"
k f x f -> commit "각", preedit "ㅏ"
```

## 9. 편집 키와 경계 입력

### 9.1 Backspace

- 활성 조합이 있으면 마지막 대표 글쇠 입력 하나를 스택에서 제거하고 남은
  입력으로 조합을 다시 계산한다.
- 이 경우 Backspace를 호스트에 전달해서는 안 된다.
- 제거 뒤 입력 스택이 비면 preedit를 비운다.
- 활성 조합이 없으면 Backspace를 호스트에 Forward한다.
- 이미 Commit된 텍스트를 입력기가 되돌려서는 안 된다.

```text
k f Backspace Flush -> ㄱ
k x Backspace f Flush -> 가
k f k Backspace Flush -> 가
```

### 9.2 Delete

- Delete는 forward delete를 뜻한다.
- 활성 조합이 있으면 `FlushThenForward(Delete)`로 처리한다.
- 활성 조합이 없으면 Delete를 즉시 Forward한다.
- Delete가 활성 조합 내부의 글쇠를 제거하는 동작으로 바뀌어서는 안 된다.

### 9.3 공백과 printable non-jamo

- Space와 호스트가 직접 printable text로 제공한 non-control whitespace는
  `FlushThenEmit`으로 처리한다.
- 한글 상태 글쇠표의 non-jamo printable scalar도 `FlushThenEmit`으로 처리한다.
- 같은 입력에서 Flush한 text와 뒤따르는 scalar는 하나의 committed text로 합쳐도
  된다.
- Flush된 조합과 뒤따르는 scalar의 순서를 바꾸거나 둘 중 하나를 잃어서는 안 된다.
- 물리 Tab과 Enter/Return 키는 호스트가 별도의 printable text 입력으로 제공하지
  않는 한 9.4의 호스트 동작 키 규칙을 따른다.

### 9.4 호스트 동작 키

- Arrow, Home, End, Page Up, Page Down, Insert, F1-F12, 물리 Tab과
  Enter/Return은 조합 입력이 아니다.
- 활성 조합이 있으면 먼저 Flush하고 키를 Forward한다.
- 활성 조합이 없으면 키를 그대로 Forward한다.
- 키의 방향, modifier, press/release 의미를 임의로 바꾸어서는 안 된다.

### 9.5 단축키

- Control, Alt, Super 또는 호스트 단축키 modifier가 포함된 조합은 한글 자모
  입력이나 Shift 단일 탭이 아니다.
- 활성 조합이 있으면 먼저 Flush한다.
- 로마자 대표 글쇠를 포함한 단축키는 component의 Colemak XKB 배열로 해석된
  원본 event를 호스트에 통과시킨다.
- modifier 집합은 보존한다. 단, Shift는 underlying 글쇠의 대소문자 또는
  shifted symbol 의미에 정상적으로 참여한다.
- 예: `k f Control(e)`는 먼저 `가`를 Commit하고 원본 `Control+f` event를 통과시킨다.
- 예: `Control(n)`은 Colemak XKB가 해석한 `Control+k` event를 통과시킨다.
- 입력기가 의미를 모르는 modifier 조합은 텍스트로 소비하지 말고 호스트에
  전달한다.

## 10. 조합 생명주기

### 10.1 포커스 이탈

- 편집 문맥이 포커스를 잃으면 그 문맥의 활성 조합을 가능한 한 해당 문맥에
  Flush한 뒤 종료한다.
- Flush할 유효한 이전 문맥이 더 이상 없고 Commit이 안전하지 않다고 플랫폼이
  명시한 경우에만 Clear할 수 있다. 이 예외는 다른 문맥에 Commit하는 것보다
  우선한다.
- 포커스를 얻은 새 문맥에 이전 preedit를 옮기거나 이전 조합을 확정해서는 안 된다.
- 새 문맥은 로마자 상태에서 시작한다.

### 10.2 입력 소스 전환과 비활성화

- 사용자가 Lisle에서 다른 입력 소스로 전환하면 활성 조합을 이전 문맥에 Flush한다.
- Lisle이 비정상 종료 또는 호스트 연결 상실 때문에 안전하게 Commit할 수 없으면
  남은 조합을 다른 문맥에 복구하려 하지 않는다.
- Lisle로 다시 돌아오면 로마자 상태이며 이전 활성 조합은 없어야 한다.

### 10.3 외부 commit 및 cancel 요청

- 호스트가 composition commit을 요청하면 활성 조합을 Flush한다.
- 호스트가 composition cancel을 요청하면 활성 조합을 Clear한다.
- commit과 cancel 요청을 같은 동작으로 취급해서는 안 된다.
- 요청 완료 뒤 preedit는 비어야 한다.

### 10.4 마우스와 caret 이동

- 마우스 클릭, touch 입력 또는 외부 caret/selection 변경이 활성 조합의 소유
  위치를 바꿀 수 있으면 먼저 Flush한다.
- 그 뒤 이동 동작은 호스트가 수행하도록 한다.
- 이전 위치의 preedit를 새 caret 위치에서 계속해서는 안 된다.

### 10.5 순서와 재진입

- 하나의 경계 입력으로 발생한 Flush는 뒤따르는 Commit 또는 Forward보다 먼저
  호스트에 관찰되어야 한다.
- 같은 이벤트가 중복 전달되거나 조합이 두 번 Commit되어서는 안 된다.
- 호스트가 Commit 또는 preedit 갱신 도중 포커스/생명주기 콜백을 다시 발생시켜도
  각 단계는 최대 한 번만 완료되어야 한다.
- 지연된 작업이 있더라도 뒤에 들어온 키가 앞 경계를 추월해서는 안 된다.
- 지연된 작업을 다른 편집 문맥에 적용해서는 안 된다.

## 11. 오류 및 불완전한 호스트 정보

- 물리 글쇠 위치를 신뢰성 있게 식별할 수 없으면 문자 값만 보고 한글 자모로
  추측해서는 안 된다. 활성 조합을 Flush한 뒤 원래 입력을 호스트에 전달한다.
- 알 수 없는 modifier 또는 키 종류는 기본적으로 Forward한다.
- preedit 갱신이 실패했지만 이전 문맥에 Commit할 수 있으면 활성 visible text를
  한 번 Commit하여 텍스트 손실을 피한다.
- Commit 성공 여부가 불명확한 경우 같은 텍스트를 무조건 재전송해서는 안 된다.
  중복 입력 방지가 손실 추정 복구보다 우선한다.
- 잘못되거나 오래된 selection/range 정보 때문에 일반 입력을 명시적 문서 위치에
  삽입해서는 안 된다. 입력기는 자신이 소유한 활성 preedit만 교체하고, 그 밖의
  Commit은 호스트의 현재 입력 위치를 사용해야 한다.
- 호스트별 예외가 필요하더라도 이 문서의 사용자 관찰 가능 계약을 바꾸어서는
  안 된다.

## 12. 적합성 예시

예시의 마지막에는 별도 표기가 없어도 최종 활성 조합을 Flush한 것으로 본다.
`Space`는 U+0020, `Forward(X)`는 호스트 동작 전달을 뜻한다.

```text
# 상태 선택
초기 상태                              -> 로마자
오른쪽 Shift 단일 탭                   -> 한글, 출력 없음
왼쪽 Shift 단일 탭                     -> 로마자, 출력 없음
오른쪽 Shift+k                         -> 현재 상태의 shifted 입력, 상태 변경 없음

# 초성 선행 모아치기
k f x                                  -> 각
k x f                                  -> 각
x k f                                  -> ㄱ가
k x Space                              -> ㄱㄱ 

# 약한 아래
j k f                                  -> 까
k j f                                  -> 까
j f k                                  -> 아ㄱ
k k f                                  -> ㄱ가

# source-key-sensitive 중성
/ f                                    -> ㅘ
f /                                    -> ㅘ
v f                                    -> ㅘ
f v                                    -> ㅏㅗ
9 t                                    -> ㅝ
t 9                                    -> ㅝ
b t                                    -> ㅝ
t b                                    -> ㅓㅜ

# 편집 경계
k f Backspace                          -> ㄱ
k f Delete                             -> 가 + Forward(Delete)
k f Left                               -> 가 + Forward(Left)
k f Escape                             -> 가 + 로마자 + Forward(Escape)
k f Control(e)                         -> 가 + Forward(Control+f)

# preedit와 commit
k                                      -> commit "", preedit "ㄱ"
k f                                    -> commit "", preedit "가"
k f x f                                -> commit "각", preedit "ㅏ"
k f x f Space                          -> commit "각ㅏ ", preedit ""

# 문맥 경계
한글 상태에서 k f 후 포커스 이탈       -> 이전 문맥에 "가" commit
새 편집 문맥 활성화                    -> 로마자, preedit 없음
한글 상태에서 k f 후 입력 소스 전환    -> 이전 문맥에 "가" commit
Lisle 재선택                           -> 로마자, preedit 없음
```

## 13. 결정 규칙

새로운 키, 호스트 동작 또는 생명주기 사례가 발견되면 다음 질문을 순서대로
적용한다.

1. 해당 입력이 현재 활성 조합의 명시된 조합 입력인가? 그렇다면 조합에서 소비한다.
2. Backspace인가? 활성 조합이 있으면 입력 스택을 한 단계 되돌리고, 없으면 Forward한다.
3. 명시적 cancel인가? 그렇다면 Clear한다.
4. printable text인가? 활성 조합을 Flush한 뒤 해당 text를 Commit한다.
5. 단축키, 탐색 키 또는 호스트 동작인가? 활성 조합을 Flush한 뒤 Forward한다.
6. 편집 문맥 종료인가? 이전 문맥에 안전하게 Flush하고 상태를 폐기한다.
7. 어느 범주인지 확정할 수 없는가? 활성 조합을 안전하게 Flush한 뒤 원래 입력을
   정확히 한 번 Forward한다.

이 규칙으로도 둘 이상의 결과가 가능하면 공통 불변조건의 우선순위를 적용한다.
새 동작이 기존 사용자 관찰 가능 결과를 바꾼다면 구현 편의로 결정하지 말고 이
문서를 먼저 개정해야 한다.
